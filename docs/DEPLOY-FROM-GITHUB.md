# استقرار از گیت‌هاب

به‌روزرسانی سرور تا امروز یعنی یک نفر ترمینال باز کند و دستور بزند. هر بار
که آن یک نفر در دسترس نبود، مغازه کد قدیمی را اجرا می‌کرد — نسخهٔ گوشی
منتشر می‌شد و سرور عقب می‌ماند، و صفحه‌های تازه خالی بالا می‌آمدند چون
سرور هنوز فیلدهایی را که آن‌ها می‌خوانند نمی‌فرستاد.

با این تنظیمات، استقرار از خودِ گیت‌هاب انجام می‌شود: **Actions ← Deploy ←
Run workflow**.

دستی است و دستی می‌ماند. این یک نانوایی در حال کار است؛ هیچ‌کس نمی‌خواهد
یک merge در ساعت چهار بعدازظهر وسط فروش روز، php-fpm را ری‌استارت کند.
تصمیمِ «کِی» با شماست؛ این فقط تایپ را انجام می‌دهد.

---

## یک بار تنظیم کنید

همهٔ کارها روی **سرور** و در **تنظیمات مخزن** انجام می‌شود.

> **کلید خصوصی را در هیچ چتی نفرستید** — نه به من، نه به کسی دیگر. مستقیم
> از سرور در تنظیمات گیت‌هاب بگذارید. کسی که آن را ببیند می‌تواند مغازه را
> بخواباند.

### ۱. یک کلید بسازید که فقط برای استقرار باشد

روی **سرور**، به‌عنوان همان کاربری که استقرار را انجام می‌دهد (`ubuntu`):

```bash
ssh-keygen -t ed25519 -f ~/.ssh/github_deploy -N '' -C 'github-actions-deploy'
cat ~/.ssh/github_deploy.pub >> ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys
```

کلید جداگانه، نه کلید شخصی خودتان: اگر روزی لازم شد جلوی گیت‌هاب را
بگیرید، یک خط از `authorized_keys` پاک می‌شود و دسترسی خودتان دست‌نخورده
می‌ماند.

### ۲. چهار مقدار را بردارید

هر چهار تا را روی سرور چاپ کنید:

```bash
echo '--- DEPLOY_SSH_KEY ---';  cat ~/.ssh/github_deploy
echo '--- DEPLOY_HOST ---';     curl -s ifconfig.me; echo
echo '--- DEPLOY_USER ---';     whoami
echo '--- DEPLOY_HOST_KEY ---'; ssh-keyscan -t ed25519 localhost 2>/dev/null | sed "s/^localhost/$(curl -s ifconfig.me)/"
```

`DEPLOY_HOST_KEY` کلید عمومیِ **خودِ سرور** است. بدون آن، اولین اتصال به هر
چیزی که جواب بدهد اعتماد می‌کند — و این اتصال کلیدی دارد که می‌تواند مغازه
را ری‌استارت کند، پس «هرچه جواب داد» کافی نیست. اگر روزی کلید سرور عوض شود،
استقرار متوقف می‌شود به‌جای آنکه بی‌صدا بپذیرد.

### ۳. در مخزن ثبت کنید

**Settings ← Secrets and variables ← Actions ← New repository secret**

| نام | مقدار |
|---|---|
| `DEPLOY_SSH_KEY` | کل خروجی `cat ~/.ssh/github_deploy` — با خط `-----BEGIN` و `-----END` |
| `DEPLOY_HOST` | آی‌پی سرور |
| `DEPLOY_USER` | معمولاً `ubuntu` — اگر همین است می‌توانید ثبت نکنید |
| `DEPLOY_HOST_KEY` | خروجی `ssh-keyscan` |
| `DEPLOY_PORT` | فقط اگر SSH روی پورتی غیر از ۲۲ است |

اگر یکی از سه‌تای اول یا `DEPLOY_HOST_KEY` جا بیفتد، workflow در همان قدم
اول با پیام روشن متوقف می‌شود و چیزی روی سرور دست نمی‌خورد.

> **حواستان به این دو باشد** — اولین استقرار دقیقاً به همین دلیل شکست خورد:
>
> - آن صفحه **دو تب** دارد: «Secrets» و «Variables». مقدار باید در
>   **Secrets** باشد. چیزی که در Variables گذاشته شود اصلاً به workflow
>   نمی‌رسد — و بدتر، مقدارش در لاگ اجرا دیده می‌شود، که برای یک کلید
>   خصوصی یعنی لو رفتن.
> - دکمهٔ درست **New repository secret** است، نه ساختن secret زیر یک
>   Environment. این workflow هیچ environmentی اعلام نمی‌کند، پس
>   secretهای environment را نمی‌بیند.
>
> اگر در Variables گذاشته باشید، workflow خودش تشخیص می‌دهد و می‌گوید.

## استقرار

**Actions ← Deploy ← Run workflow**. شاخه را خالی بگذارید تا `main` مستقر شود.

چه اتفاقی می‌افتد:

1. اتصال آزمایش می‌شود — کلید یا آدرس غلط، همین‌جا شکست می‌خورد و سرور
   دست‌نخورده می‌ماند.
2. `scripts/deploy.sh` روی سرور اجرا می‌شود: کد، وابستگی‌ها، مهاجرت‌ها،
   کش‌ها، ری‌لود، بررسی سلامت.
3. در پایان می‌گوید همین حالا چه کامیتی روی سرور است — حتی وقتی استقرار
   شکست خورده باشد، چون اولین سؤال بعد از هر شکست همین است.

مهاجرت‌های معلق پشت `artisan down` اجرا می‌شوند و اگر شکست بخورند کد به
کامیت قبلی برمی‌گردد. نسخه‌ای که مهاجرت ندارد اصلاً مغازه را نمی‌بندد.

اگر کسی روی سرور فایلی را دست‌نویس تغییر داده و ثبت نکرده باشد، استقرار
**پیش از هر کاری** متوقف می‌شود و همان فایل‌ها را نشان می‌دهد. کشیدن کد
تازه روی کار دست‌نویس یا وسط راه می‌شکند یا بی‌صدا دورش را می‌گیرد، و این
پوشه وقتی کنار تنور دنبال مشکلی می‌گردند دست‌کاری می‌شود.

> **بار اول:** سرور هنوز نسخهٔ قبلی `deploy.sh` را دارد که آرگومان نمی‌گیرد
> و هرچه بگویید `main` را مستقر می‌کند. از بار دوم به بعد `ref` کار می‌کند.

## اگر شکست خورد

| پیام | معنی |
|---|---|
| `این secretها خالی رسیدند` | تب اشتباه (Variables به‌جای Secrets)، یا Environment secret به‌جای Repository secret، یا نام غلط — خودِ پیام می‌گوید کدام |
| `Host key verification failed` | کلید سرور عوض شده — **بررسی کنید چرا** پیش از آنکه `DEPLOY_HOST_KEY` را عوض کنید |
| `Permission denied (publickey)` | کلید در `authorized_keys` سرور نیست |
| `Connection timed out` | آی‌پی یا پورت اشتباه، یا فایروال |
| `API سالم جواب نداد` | استقرار انجام شد ولی مغازه بالا نیامد — لاگ کامل را در همان اجرا ببینید |

## استقرار شبانه، بدون اینکه کسی چیزی بزند

اگر workflow بالا به هر دلیلی اجرا نشود — یا اصلاً نخواهید به گیت‌هاب
کلید بدهید — سرور می‌تواند خودش بپرسد. `scripts/auto-deploy.sh` هر شب
یک بار از گیت‌هاب می‌پرسد چیز تازه‌ای هست یا نه، و اگر بود `deploy.sh` را
می‌زند. نه کلیدی لازم دارد، نه secretی، نه اجازه‌ای از گیت‌هاب.

**شبانه، نه هر چند دقیقه — و این یک تصمیم است نه تنبلی.** استقرار عمداً
دستی بود: هیچ‌کس نمی‌خواهد یک merge ساعت چهار بعدازظهر وسط فروش،
php-fpm را ری‌استارت کند، و مهاجرت مغازه را برای چند ثانیه می‌بندد. پس
ساعتی که تنور سرد است. هر چیزی که زودتر لازم باشد، همان دو خطی است که
یک آدم می‌زند.

روی سرور، به‌عنوان `ubuntu`:

```bash
sudo touch /var/log/bakery-auto-deploy.log
sudo chown ubuntu /var/log/bakery-auto-deploy.log
crontab -e
```

و این یک خط (ساعت ۳ بامداد):

```
0 3 * * * /bin/bash /home/ubuntu/bakery-management-system/scripts/auto-deploy.sh
```

چه می‌کند و چه نمی‌کند:

| حالت | رفتار |
|---|---|
| چیز تازه‌ای نیست | هیچ — حتی در لاگ چیزی نمی‌نویسد |
| کد تازه هست | `deploy.sh` را می‌زند و نتیجه را می‌نویسد |
| استقرار شکست بخورد | با خطا تمام می‌شود و می‌نویسد؛ **تا شب بعد دوباره تلاش نمی‌کند** |
| کسی روی سرور فایلی را دست‌نویس عوض کرده | دست نمی‌زند و علتش را می‌نویسد |
| کسی همان لحظه دستی مستقر می‌کند | کنار می‌کشد |

لاگ خالی یعنی شب‌های آرام. لاگی که هر شب یک خط «چیزی نشد» بنویسد، شبی
که واقعاً چیزی شده را کسی نمی‌خواند.

خواندن لاگ:

```bash
tail -40 /var/log/bakery-auto-deploy.log
```

۱۷ بررسی در `scripts/tests/auto_deploy_test.sh`، روی هر شش حالت بالا.

## برگرداندن

اگر نسخه‌ای مشکل داشت، همین workflow را با `ref` برابر تگ نسخهٔ سالم قبلی
اجرا کنید — مثلاً `v4.88.0`. سرور روی همان تگ می‌ایستد و خودش می‌گوید که
دیگر روی `main` نیست؛ برای برگشتن، استقرار بعدی را با `main` بزنید.

روی سرور هم همین کار با یک آرگومان انجام می‌شود:

```bash
bash scripts/deploy.sh v4.88.0
```

**برگرداندن کد، مهاجرت‌ها را برنمی‌گرداند.** اگر نسخهٔ بد ساختار دیتابیس را
عوض کرده بود، کدِ قدیمی در برابر ساختار جدید اجرا می‌شود. برای نسخه‌ای که
مهاجرت داشته، پیش از برگرداندن بپرسید.
